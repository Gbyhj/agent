# Code Review Checklist

> 参考: Google Critique · 代码被读的次数远多于被写的次数

## 每次 PR 必须检查

### 🔴 阻塞项（必须修）

- [ ] **安全**: 是否有注入漏洞、路径遍历、密钥泄露？
- [ ] **正确性**: 逻辑是否正确？边界条件是否处理？
- [ ] **测试**: 是否写了对应的测试？
- [ ] **破坏性变更**: API 是否后向兼容？如果不兼容，CHANGELOG 是否标记？

### 🟡 重要项（应该修）

- [ ] **可读性**: 新人能在 5 分钟内理解吗？（Google 标准）
- [ ] **类型标注**: 公共函数是否有完整 type hints？
- [ ] **日志**: 是否用 logger 而非 print()？
- [ ] **错误处理**: 异常是否有友好提示？是否可恢复？
- [ ] **性能**: 是否有不必要的文件 I/O 或重复调用？

### 🟢 建议项（可选）

- [ ] **代码行数**: 单文件是否超过 300 行？是否应拆分？
- [ ] **命名**: 变量/函数名是否自解释？
- [ ] **注释**: 复杂逻辑是否有注释？
- [ ] **文档**: 公共 API 是否有 docstring？

## 审查流程

```
Author:  创建 PR → 填写 Checklist → 指派人
Reviewer: 逐项检查 → 提出意见 → Approve / Request Changes
Author:  修改 → 回复意见 → 重新请求审查
Merger:  所有检查通过 → Squash Merge
```

## 特殊场景

### 架构变更
- [ ] 是否更新 BLUEPRINT.md？
- [ ] 是否影响其他模块？是否通知相关 owner？

### 安全敏感代码
- [ ] 沙箱路径验证
- [ ] 用户数据隔离 (user_id)
- [ ] API Key 处理（不进日志）

### 性能敏感代码
- [ ] 是否有基准测试？
- [ ] 是否考虑缓存？
- [ ] 是否有内存泄漏风险？
